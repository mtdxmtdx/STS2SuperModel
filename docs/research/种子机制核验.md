# StS2 种子机制核验（面向 Expectimax）

核验日期：2026-08-24  
适用项目：`D:\STS2BestChoice\STS2BestChoice`（当前 README 标注按 StS2 v0.110.x 编译）与 `reference\sts2-cli`。

## 结论摘要

1. **种子机制对训练有用，但不能替代当前回合的随机状态。** CLI 可以用固定字符串 seed 启动真实游戏引擎，适合批量生成可复现实验；当前回合的 Expectimax 若要复现已发生到一半的牌局，必须保存/捕获各 RNG 流的当前状态和消费位置，而不是只保存 run seed。
2. **v0.107.1 的关联随机性修复有官方依据。** Mega Crit 的官方 Steam 更新说明明确写出：每局有一个 12 字符 run seed，但包含多个由 run seed 派生的 PRNG；v0.107.1 将实现替换为 `xoshiro256**`，并称散点图不再显示人类可检测的相关性。该结论只适用于该版本之后的实现，不能据此断言所有 RNG 流统计上完全独立或未来版本不变。
3. **原研究稿关于存档重建“只要恢复主种子即可精确重建后续 RNG”是不成立的。** `sts2-save-rebuild` 的 README 明确说重建存档使用新的 RNG 状态；下游商店、奖励、事件和抽牌会进入“平行宇宙”，要字节级回放需要 headless simulator。
4. **StableShuffle、decimal、AutoSlayer 等主张目前没有足够一手证据。** 在本地项目、CLI、官方更新说明和列出的外部仓库中，没有找到能证明 StS2 全局使用 `decimal`、存在名为 `StableShuffle` 的统一洗牌流程或内置 `AutoSlayer` 模块的证据。它们不应作为模型设计前提。
5. **当前阶段应继续使用 Expectimax。** 已有项目 ADR 和实现已经定义“机会节点按概率、机会分支后重新取最大后续策略”的语义；随机分支上限、采样、概率质量和置信区间必须保留。种子研究的直接用途是生成可复现实验集、分组回归测试和检查 RNG 消耗，而不是把 seed 当作策略输入。

## 逐条核验

### A. 固定 seed 与真实 headless 引擎

**本地一手证据**

- `reference/sts2-cli/README.md` 的 JSON 协议示例接受 `{"cmd":"start_run", ..., "seed":"test"}`，并说明 CLI 运行真实游戏引擎，伤害、卡牌、敌人 AI、遗物和 RNG 与实机一致。
- `reference/sts2-cli/src/Sts2Headless/RunSimulator.cs:232-251`：`StartRun` 将输入字符串保存为 `seedStr`，传入 `RunState.CreateForTest(..., seed: seedStr)`。
- `RunSimulator.cs:506-515`：加载存档时读取 `SerializableRng.Seed` 并调用 `RunState.FromSerializable`；这证明 seed 是存档字段，但没有证明仅恢复 seed 就能恢复 RNG 的当前状态。

**判断**

固定 seed 很适合训练数据的“实验条件”或从新 run 开始的完整对局回放。对中途战斗状态，仍需 RNG 快照；从 seed 重新开始并不能跳过此前已经发生的 RNG 消耗。

### B. 多 PRNG 流与关联随机性

**官方一手来源**

- [Major Update #2 - v0.107.1（Mega Crit Steam 公告）](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1835871199305790)：官方说明每局有 12 字符 run seed，但实际包含多个分别影响牌库抽取、战斗奖励、事件选择等内容的 PRNG；v0.107.1 用 `xoshiro256**` 替换旧 PRNG，并指出结果散点图不再显示人类可检测的相关性。
- [Beta Patch Notes - v0.108.0（Mega Crit Steam 公告）](https://steamstore-a.akamaihd.net/news/externalpost/steam_community_announcements/1836506165569491)：官方再次记录“Fixed many instances of weird RNG behavior (shoutout again to tckmn!)”，并说明多人 Daily Run 的事件 RNG seed 一致性修复。说明 v0.107.1 后 RNG/同步仍在继续修复，版本锁定很重要。

**外部技术来源**

- [tckmn: Correlated randomness in Slay the Spire 2](https://tck.mn/blog/correlated-randomness-sts2/)：文章给出 v0.107.0 时代的实证案例（Underdocks + Neow's Bones 的 Debt 约 54%、Trash Heap 不出 Rebound、首场战斗药水概率 76% vs 4%），并展示“run seed + 字符串哈希”派生多流的简化模型。文章是逆向分析，不是官方规范；文中的概率和调用关系应视为版本限定的研究结果。
- [tckmn/sts2-seed-search](https://github.com/tckmn/sts2-seed-search)：仓库提供 `cleaned-v0.107.0.c`、`cleaned-v0.107.1.c`、`uncleaned-v0.108.0.c` 等版本化 C 搜索程序，证明这些研究依赖具体版本实现；仓库 README 仅给出编译/统计用法，不能作为当前 v0.110 RNG 规范。

**判断**

应记录 `game_version`、`run_seed`、RNG 流名、四个 xoshiro 状态字和消费计数。不要假设跨版本、跨流或跨模组的 RNG 调用顺序不变。v0.107.1 修复了已知相关性，但 Expectimax 仍按分支概率计算，不应把“看起来均匀”当作独立性证明。

### C. 存档是否能恢复后续随机序列

- [MufanQiu/sts2-save-rebuild README](https://github.com/MufanQiu/sts2-save-rebuild)：`What you get back` 表格把 character/deck/relics/HP/gold/map/seed 列为可恢复，但把“RNG state for upcoming shops / draws”列为 **no — parallel universe**；文中明确写出重建 run 使用 fresh RNG state，后续商店、奖励、事件和抽牌会不同。

**判断**

原研究稿第 3.2 节应改为：历史文件可帮助恢复 seed 和局面元数据，但该工具不恢复 RNG 游标/流状态，不能用于字节级随机回放。训练数据若从局面中断恢复，必须同时保存完整 RNG 快照，或者改用 CLI 从 run 起点重新生成。

### D. Spire Codex 的证据范围

- [ptrlrd/spire-codex README](https://github.com/ptrlrd/spire-codex)：说明其通过 GDRE Tools 提取 PCK、ILSpy 反编译 `sts2.dll`，再从 C# 源码解析卡牌、事件、敌人状态机和 `NextInt`/`NextFloat` 调用点，并提供版本化数据。

**判断**

它适合作为卡牌/事件/敌人规则和 RNG 调用点的索引，不能单独证明“StableShuffle”“全程 decimal”或某一版本的完整 RNG 派生算法。使用时必须绑定具体游戏版本和原始反编译文件。

### E. 本项目已有实现与 Expectimax 语义

- `STS2BestChoice/docs/adr/0002-shadow-rng-expectimax.md`：已接受的设计决定是捕获七条 `RunRngSet` 流为独立序列化 xoshiro256** 状态；未知随机结果作为 chance node；最多 32 个结果精确枚举，超过阈值采用分层采样并报告 95% 区间；chance 分支后重新选择最大后续动作。
- `STS2BestChoice/STS2BestChoice.Core/Model/RandomModel.cs:1-90`：定义四个 `ulong` 状态字、`Counter`、`IsKnown`、`NextInt`（使用 128 位乘积高半部的 bounded mapping）以及七个流名。
- `STS2BestChoice/Mod/LiveCombatSnapshotAdapter.cs:3049-3078`：从 `RunRngSet` 读取 `Shuffle`、战斗卡牌/药水生成、卡牌选择、能量费用、目标、充能球七条流；读取失败时标记 `IsKnown=false` 并追加限制原因。
- `STS2BestChoice/STS2BestChoice.Core/Search/ExpectimaxEngine.cs:7-105`：接口明确区分 `Apply` 产生的 `ChanceBranch`，按概率归一化求期望，超过 `MaximumChanceBranches` 时截断并标记不完整。

**判断**

当前实现方向与种子研究的可靠部分一致：用真实/已捕获的 RNG 状态驱动确定性分支，用 Expectimax 处理未观察结果；不把 RandomForeseer 作为依赖，也不以 run seed 代替战斗 RNG 快照。

## 对模型制作的建议

### 训练样本最小字段

```json
{
  "game_version": "0.110.x",
  "run_seed": "...",
  "combat_state": "...",
  "rng_streams_before": {"CombatTargets": {"state0": 0, "state1": 0, "state2": 0, "state3": 0, "counter": 0}},
  "action": "...",
  "outcomes": [{"label": "...", "probability": 0.5, "next_state": "..."}],
  "objective": "balanced|damage|minimum_loss",
  "confidence": "Reliable|Estimated|Uncalculable"
}
```

- `run_seed` 用于从头重放和分组划分，不作为唯一 RNG 输入。
- `rng_streams_before/after` 用于证明一个转移是否消费了正确的流和次数。
- `outcomes` 是 Expectimax 的 chance 分支；每个分支之后都重新求 max continuation。
- `game_version` 必须进入数据集键，避免把 v0.107.x 与 v0.110.x 的规则/RNG 混训。

### 必做验证

1. 同一 CLI seed 从新 run 启动多次，比较 JSON 状态/动作日志是否一致；以日志为证据，不只比较最终胜负。
2. 对同一实机中途状态，比较 RNG 快照驱动的影子转移与下一次真实结果；按七条流分别统计消费计数。
3. 对 v0.107.1 以前和以后分别建立回归集；旧版关联 RNG 案例只能用于历史分析，不能混入当前策略训练。
4. 对大于 32 个结果的采样分支记录抽样种子、样本数、概率质量和置信区间，禁止把估算分支标成严格最优。

## 未证实或应删除的原稿表述

| 原稿表述 | 核验结果 |
|---|---|
| “12 字符/64 位主种子可单独重建全部未来状态” | 部分错误。12 字符 run seed 确实由官方说明，但中途未来 RNG 还依赖各流当前状态和消费位置。 |
| “全程使用 decimal 保证跨平台物理级确定性” | 未找到 StS2 一手证据；不要作为模型前提。 |
| “StableShuffle 按固定 ID 预排序” | 未找到本地或官方一手证据；需从对应版本反编译代码逐点证明后才能保留。 |
| “内置 AutoSlayer 哑随机 headless Bot” | 未找到本地或官方一手证据；CLI 的 headless 能力不能证明游戏内置该模块。 |
| “xoshiro256** 使所有子系统统计独立” | 过强。官方只说散点图不再显示人类可检测的相关性；仍需按版本验证流派生和调用顺序。 |
| “存档反序列化可精准恢复后续 RNG” | 与 `sts2-save-rebuild` README 直接冲突，应删除或改成“恢复元数据但 RNG 为新状态”。 |
